原来的异常边界确实过粗：读取 HTTP 故障可能形成持久全局暂停，研究步骤缺少统一持久化结果，部分材料写入中断无法完整续接，错误日志缺少请求定位信息。本次已修改这些机制，并部署、重启两次后读取验证。

## 修改内容

| 环节 | 新行为 | 保留的限制 |
| --- | --- | --- |
| HTTP 读取 | 记录实际状态码、业务码、请求 ID、方法、脱敏路径、耗时；阻断当前轮次，后续重新读取核对 | 鉴权失败单独标识；没有有效读取时不执行 |
| 研究、资讯、扫描 | 独立工作线程与组件状态，失败不形成永久执行暂停；失败资讯不更新成功观察时间 | 行情、数据与执行门槛不因研究失败而放宽 |
| 策略及数据 | 单策略、单执行数据组隔离；可验证组独立发布；期权标的日线单独校验 | 冻结种子不修改，不自动批准历史修订 |
| 下单回执 | 未确认意图与暂停同事务保存；找回同一券商订单、核对持仓/累计成交及现金风控后才清除对应可恢复暂停 | 没查到回执不重发原买卖单；手动、风险、账本冲突暂停不自动解除 |
| 期权回执 | 修复异常捕获覆盖原有恢复政策的问题 | 其他未确认委托存在时仍禁止新增执行 |
| 撤单 | 有界重试后冷却五分钟；重新读回同一有效委托后再撤 | 不以撤单响应代替最终成交核对 |
| 存储 | SQLite WAL 与 FULL 同步，普通读取不抢写锁；报告与数据采用 fsync 和原子替换 | 账本仍是订单与资金的事实来源 |
| 过期观察 | 无法合法封存的 Shadow 归档失败，避免残留 pending 永久触发休市轮询 | 不补造过去的未来观察或成交 |

### 检查点如何恢复

- 步骤绑定工作流版本、交易日、数据目录和内容哈希、设置哈希。结果和完成状态同事务提交。
- 已完成步骤复用原结果；失败步骤持久化退避，30 秒起、最多 30 分钟。调度周期仍会影响实际重试时刻。
- AI 复盘保存原始证据包及返回结果，报告发布失败后复用，不重新生成一份不同的分析。
- 进程被强制结束时，操作系统释放工作流/步骤锁；下次执行恢复残留 running 步骤。
- 历史下载按标的保存进度；未部署候选源文件通过模板、表达式和因果检查恢复或归档；不执行候选源文件。
- **不能恢复大模型推理到一半的内部状态。** 未完成请求需要重新调用；已成功保存的结果可以复用。券商订单始终先核对，不能靠重放研究检查点再次下单。
- 旧任务不会被伪造为新检查点。本次实际执行了 `execution_cache_audit`，校验 10 个冻结策略和 NVDA/QQQ 期权信号日线，随后用禁止执行的回调再次调用，证实直接复用了保存结果；第二次服务重启后仍为 completed、attempts=1。

### 原来的日志为什么不足

此前 SQLite 已有事件，不能称为完全没有日志；问题是 HTTP 失败只保留异常类型和少量调用栈，无法还原状态码或接口，stdout/stderr 也不足以按请求追踪。此前的 HTTPError 不能追溯推断成 502。

现在本机 `~/.local/share/stock-agent/quant-agent/logs/runtime.jsonl` 保存结构化请求和任务事件，5 MiB/文件、保留 6 个文件。目录权限 0700、文件 0600；不记录签名、私钥、请求正文、查询参数或原始模型 stderr。SQLite 保留订单、成交、检查点及事件，文件轮转不删除这些事实。

看板 **运行 → 恢复与检查点** 展示局部故障、尝试次数、下次重试、完成结果、中断续跑及日志写入状态。
